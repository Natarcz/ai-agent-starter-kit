Проведи строгое инженерное код-ревью изменений перед коммитом.

**Scope:** `git diff` (unstaged + staged). Если нужен контекст — `git diff origin/main...HEAD`.

Проверь по правилам `CLAUDE.md`:

1. **Безопасность:** утечки ключей/токенов, секреты в коде или логах, prompt injection (пользовательский ввод в системном промпте), PII в логах.
2. **Типизация и контракты:** `Any`, нетипизированные `dict`/`object` на границах API, изменение контракта без обновления схемы.
3. **Ошибки и устойчивость:** пустые `except`/`catch`, сетевые вызовы без таймаута, retry без backoff, не-обработанный offline.
4. **Мобильная специфика:** блокировки main/UI thread, утечки подписок/listeners, поллинг вместо events, фоновые задачи не через системный планировщик.
5. **LLM-стоимость:** новые LLM-вызовы без оценки токенов, отсутствие логирования usage.
6. **Тесты:** новая бизнес-логика без edge-case тестов, ослабленные assertions, моки, подогнанные под бажный код.

**Формат вывода (без воды):**

- `[CRITICAL]` `file:line` — баг, уязвимость, нарушение гардрейла (блокирует коммит)
- `[IMPROVEMENT]` `file:line` — оптимизация производительности, читаемости, стоимости
- `[OK]` — что реализовано корректно (1–3 пункта)

Каждый finding — с путём к файлу и номером строки. Если нарушений нет — так и скажи, не выдумывай проблемы.
