## Шаг 1 — уточнение

Если задача неоднозначна (непонятно «что», «где» или «для кого»), НЕ гадай —
задай 1-3 конкретных уточняющих вопроса и остановись. План по неверной
интерпретации хуже отсутствия плана.

## Шаг 2 — исследование

Изучи релевантный код (`CLAUDE.md` → Project Map → нужные файлы). Если задача
большая — используй субагентов по `AGENTS.md` (Planner-роль: только чтение).

## Шаг 3 — план

Выведи в формате:

## Plan

**Цель:** одна строка — что должно получиться.

**Масштаб:** S / M / L + оценка (файлов, примерный объём). По `AGENTS.md`:
L-задачи с непересекающимися файлами → кандидаты на субагентов.

**Изменения:**
- `file/path` — что именно меняется и зачем (по файлам, не абстрактно)

**Контракты и зависимости:**
- какие API-модели/эндпоинты/схемы затрагиваются, нужна ли версионирование
- новые зависимости, если есть — с обоснованием

**Риски:**
- что может сломаться, edge cases, миграции данных
- затрагивает ли protected paths (`.github/workflows/`, деплой-конфиги) —
  если да, отметь и запроси подтверждение

**Приёмка:**
- конкретные проверяемые критерии «готово» (тесты, команды, поведение)

**Вне scope:**
- что явно НЕ делаем в этой задаче

## Правила

- План должен быть самодостаточным: Implementation-субагент или другой
  разработчик реализует по нему без дополнительного контекста.
- Не пиши код — только решения, границы и критерии.
- Если задача тривиальна (1-2 строки) — скажи об этом и предложи пропустить план.
