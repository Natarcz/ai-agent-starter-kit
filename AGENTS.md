# Multi-Agent Orchestration & Subagents

Правила координации параллельных агентов. Конвенции кода — в `CLAUDE.md`, этот файл отвечает только за то, *как* агенты работают вместе.

## Приоритет правил

1. Прямые инструкции пользователя в чате — выше всего.
2. `CLAUDE.md` — конвенции проекта.
3. Этот файл — координация агентов.
4. Поведение модели по умолчанию.

При конфликте `CLAUDE.md` и этого файла побеждает `CLAUDE.md`.

## Когда использовать субагентов

Субагенты — не дефолт, а инструмент для задач, которые не помещаются в один контекст:
крупные фичи, рефакторинг нескольких модулей, параллельные независимые работы.
Маленькая задача в одном-двух файлах — выполнять напрямую: три агента утраивают расход токенов без выигрыша в качестве.

## Роли субагентов

Файлы ролей лежат в `.claude/agents/` — Claude Code подхватывает их как
переиспользуемых субагентов. Для оркестрации, не поддерживающей файлы ролей,
описания ниже служат промпт-шаблонами.

Для крупных фич и рефакторинга — параллельный запуск 3 субагентов в изолированных контекстах:

1. **Architect / Planner** — изучает структуру модулей и `CLAUDE.md`, декомпозирует задачу на атомарные шаги, проверяет контракты API. Ничего не пишет в код.
2. **Implementation** — пишет код строго по утверждённому плану, в рамках выданных файлов.
3. **QA & Security** — работает в две фазы:
   - *Параллельно с Implementation:* пишет юнит-тесты и моки по контрактам из плана (TDD-подход) — тесты готовы до/во время кода.
   - *После завершения Implementation:* проверяет итоговый `git diff` на утечки секретов, блокировки main thread и нарушение `CLAUDE.md`. Read-only по отношению к продакшн-коду.

## Правила параллелизации

- **Параллелить только при непересекающихся наборах файлов.** Если два агента трогают одни файлы или один зависит от результата другого — выполнять последовательно.
- **Один агент — одна задача.** Не давать двум агентам одну и ту же задачу.
- **Субагенты не коммитят и не пушат.** Коммит делает только основной агент после проверки результатов.
- **Делегирование — самодостаточное.** Субагент не видит наш диалог: в промпт передаются задача, границы файлов, уже принятые решения, пути к релевантному коду и ожидаемый формат результата. Не «сделай как обсуждали», а полный контекст.
- **Верификация обязательна.** Отчёт субагента — не доказательство. Основной агент проверяет `git diff`, запускает тесты и только потом принимает результат.
- **Конфликты решает основной агент.** Если результаты субагентов пересекаются — основной агент мерджит и разруливает, а не перезапускает всех.

## Эскалация при blocked

Если субагент вернул `blocked`:

1. Перезапустить с расширенным контекстом (добавить файлы/решения, которых не хватило).
2. Если контекст не помог — выполнить шаг самостоятельно или разбить задачу мельче.
3. Если задача требует решения человека (доступы, архитектурный trade-off) — эскалировать пользователю, не импровизировать.

## Формат результата субагента

Каждый субагент возвращает структурированный отчёт:

```
Status: done | blocked | partial
Files changed: <список или "none">
Findings: <что сделано / что найдено, с путями и строками>
Next steps: <что нужно сделать основному агенту>
```

`blocked` требует явной причины — субагент не должен молча останавливаться.
