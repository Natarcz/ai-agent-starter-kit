# Project Context

Универсальный каркас для клиент-серверных и мобильных приложений с ИИ-агентами. Приоритеты: предсказуемая архитектура, строгая валидация контрактов API, контроль стоимости токенов.

## Project Map

- `mcp_tools/` — кастомные MCP-инструменты агента (проверка API, health-эндпоинты).
- `.claude/commands/` — slash-команды для агента (`/review-pr`, `/plan`, `/test-edge-cases`).
- `.claude/agents/` — файлы субагентов (planner / implementer / qa-security).
- `.claude/skills/` — авто-вызываемые скиллы агента.
- `.mcp.json` — регистрация MCP-серверов проекта для агента.
- `.cursor/rules/` — правила для Cursor Agent (`alwaysApply` + scoped по glob).
- `.github/workflows/` — CI, включая AI-ревью Pull Request'ов.
- `scripts/` — утилиты автоматизации (`ai_review.py` — ИИ-ревьюер PR для CI).

Проектные правила конкретного слоя живут рядом с кодом: `CLAUDE.md` в подпапке или scoped-файл в `.cursor/rules/` грузятся только при работе с этими файлами. Корневой `CLAUDE.md` держим универсальным — только то, что актуально каждой сессии.

## Commands

- Установка: `pip install -e ".[dev]"` (dev — для pytest)
- Тесты: `pytest tests/`
- MCP-сервер: `api-health-mcp` или `python mcp_tools/api_health_mcp.py`
- Ключи — только из env (`ANTHROPIC_API_KEY` и т.п.), никогда не в коде и не в git.

## Engineering Rules

### Общие (клиент-сервер и мобильные)

1. **Типизация и контракты.** Модели данных и ответы API — только через pydantic-модели или TypedDict. Запрещены `Any`, `dict` без схемы, нетипизированные `object` на границах API. Изменение контракта = обновление схемы и версионирование в том же изменении, не «потом».
2. **Ошибки и устойчивость.** Пустые `except`/`catch` запрещены — минимум логирование + проброс или явный fallback. Каждый сетевой вызов: явный таймаут, retry только для retriable-ошибок с экспоненциальной задержкой и jitter, graceful degradation при offline. Внешние API — с circuit breaker или ограничением частоты.
3. **Безопасность.** Секреты — только env-переменные или secret manager; никогда в коде, git и логах. В логи не писать токены, ключи, PII. Пользовательский ввод валидируется на границе и не попадает в системный промпт LLM без санитизации (защита от prompt injection).
4. **Стоимость и качество LLM.** Перед добавлением LLM-вызова оцени расход in/out токенов и выбери самую дешёвую модель, подтверждённую замерами на задачах проекта. Логируй usage (модель, токены, latency) для каждого вызова — без этого стоимость не посчитать.
5. **Зависимости и детерминизм.** Новая зависимость — только после подтверждения плана (см. ниже). Тесты не должны зависеть от реальных внешних сервисов — моки обязательны.
   - **Test Integrity.** Запрещено ослаблять assertions, удалять падающие тесты или подгонять моки под бажный код ради зелёного CI. Если тест упал — чини логику, а не тест (кроме явного изменения требований).

### Мобильные приложения

6. **Main thread.** Сеть, диск, тяжёлые вычисления и LLM-вызовы — только вне main/UI thread. Главный поток — только UI-обновления. Проверять на ANR (Android, >5 сек блокировки) и watchdog (iOS).
7. **Батарея и радио.** Сетевые запросы батчить; при offline — экспоненциальный backoff, а не повторы. Никаких foreground-сервисов и таймеров для фоновой работы — WorkManager/JobScheduler (Android), BGTaskScheduler (iOS).
8. **Offline-first.** Данные кэшируются локально (Room/CoreData/аналог); пользовательские действия ставятся в очередь и синхронизируются при восстановлении сети. Приложение обязано быть полезным без сети.
9. **Память и размер.** Без утечек: отписываться от listeners/observables, освобождать контроллеры и подписки. Изображения — даунскейл под размер вью, кэш с лимитом. Следить за ростом размера приложения (тяжёлые нативные либы — только с обоснованием).
10. **Платформенные конвенции.** UI следует HIG (iOS) / Material (Android); разрешения запрашиваются в контексте с объяснением, а не пачкой при старте.
11. **AI на устройстве vs в облаке.** Тяжёлые LLM-пайплайны и RAG — на бэкенде, не в мобильном клиенте (батарея, трафик, защита ключей и промптов). На устройстве — только лёгкие задачи: on-device классификация (CoreML / LiteRT), STT/TTS, стриминг ответов по SSE/WebSocket.

## Output & Communication Style

- **Be Concise.** Отвечай по делу, без вступлений и пересказа задачи. При правке кода показывай только изменённый фрагмент или diff — не дублируй весь файл без запроса.
- **No Unsolicited Refactoring.** Меняй только то, что относится к текущей задаче. Попутные улучшения выноси списком в конец ответа, не внося в код.

## Agent Workflow

### Типы задач

- **Вопрос / исследование** («как устроено X?») — сначала найди и прочитай код, ответь с ссылками на файлы. Не пиши код, пока не попросили.
- **Багфикс** — воспроизведи проблему (тест или ручной прогон), найди root cause, минимальный фикс + регрессионный тест по схеме red → green: сначала тест падает на бажном коде, потом проходит на исправленном. Тест, который никогда не падал, ничего не доказывает. Не рефактори попутно.
- **Фича / рефакторинг** — Plan First (ниже), затем реализация по плану, затем тесты, затем `/review-pr`.
- **Новая зависимость или архитектурный слой** — только после утверждённого плана.

### Обязательные шаги

- **Plan First.** Перед изменением архитектурных слоёв или добавлением зависимостей — сформируй краткий план (что меняется, какие файлы, какие риски, как проверить) и дождись подтверждения.
- **Test Coverage.** Новая бизнес-логика → юнит-тесты на граничные случаи в том же изменении.
- **Review.** Перед коммитом прогони `/review-pr` (`.claude/commands/review-pr.md`). Коммит — только после `[OK]` или осознанного принятия findings.
- **Protected Paths.** `.github/workflows/`, деплой-конфиги — не изменять без прямого запроса инженера.
- **Legal / Compliance.** Изменения, влияющие на правовой статус (платежи, донаты, персональные данные, лицензии) — не реализовывать молча: эскалировать владельцу/юристу, это не продуктовая, а юридическая задача.
- **Честность о непроверенном.** Если не запускал тесты/сборку — скажи об этом явно и приведи команды и вывод, если запускал. «Протестировано» без доказательств = не протестировано.
- **Захват знаний.** После неочевидного бага или инцидента запиши root cause и способ проверки в `CLAUDE.md`/`AGENTS.md` или docs — следующая сессия не должна наступить на те же грабли.
- **Context Hygiene.** Не читай целиком lock-файлы (`package-lock.json`, `Podfile.lock`), логи сборки и сгенерированные директории (`build/`, `.gradle/`, `DerivedData/`). Используй поиск по паттерну и чтение диапазонов строк. При смене подзадачи фиксируй промежуточный прогресс в чек-лист, чтобы не раздувать контекст.

### Верификация по типу изменения

- **Масштаб проверки = масштаб изменения.** Во время работы — узкий прогон (один тест-файл, линт изменённых файлов); перед мержем/коммитом — полный набор для затронутой стороны. «Прогнал один тест» ≠ «проверено».
- **Багфикс** — red → green (см. Типы задач): тест падает на бажном коде, проходит на фиксе; плюс прогон всего тест-сьюта затронутой стороны — фикс, ломающий соседние тесты, не фикс.
- **Перфоманс/поведение** — измеряй до и после: одна машина, одни данные, одна переменная. «Стало быстрее» на ощущениях не принимается — только цифры.
- **Баг, зависящий от данных** — воспроизводи на реальных данных (дамп, read-only запрос к прод), а не рассуждениями по коду.
- **Проверить локально невозможно** (prod-only инфраструктура, гонки под нагрузкой) — скажи об этом явно в коммите/PR и опиши, что сделал вместо проверки. Молчание читается как «проверено».
- **Green locally = mergeable.** Полный локальный набор для затронутой стороны — обязательный gate перед мержем; CI не заменяет локальную проверку.
- **Версии как в CI.** Проверяй теми же версиями инструментов и той же областью, что CI (pinned linter, те же директории). «Зелёный» локальный прогон на `@latest` может не совпадать с CI.
- **Baseline — только вниз.** Если в проекте есть зафиксированный baseline ошибок (lint/mypy/coverage), его можно понижать при исправлениях, но никогда не повышать ради зелёного прогона.

### Definition of Done

Задача закрыта, когда: код соответствует Engineering Rules, тесты на edge cases написаны и проходят, `/review-pr` не выдал `[CRITICAL]`, изменения не трогают protected paths без запроса.
